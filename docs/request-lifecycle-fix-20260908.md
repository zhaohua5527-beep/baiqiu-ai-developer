## 结论

已修复可重现的应用接入问题：中断请求被自动拼到下一问题前面；历史运行指令重复发送；原生运行时合并用户消息后重新带回已清理的包装；普通对话携带无归属的旧工作目标；有响应数据却因没有正文而被当作“30秒无响应”终止。

这不等于对话已经足够快。真实 GLM 测试仍存在明显的正文生成等待，中间版本还复现过超过两分钟无公开输出。不能据此宣称所有供应商稳定、首次回复能在一秒出现，或给出普遍加速百分比。

## 已证实的原因

1. 原生 ACP 在中断后将旧 `interrupted_prompt_text` 与新输入拼接，分隔符为 `User correction/guidance after interrupt:`。历史原始用户包装从 8,593 → 16,823 → 24,365 字符增长，后一次完整包含前一次。证据：原生会话 `92d039b5-fcd6-4c5a-9c10-29ed0cc8d9a1`，SQLite 消息 736、737、741。
2. 历史用户消息保留了整份 `[Runtime context]`，包含重复的最近对话快照。此前通过 `api_content` 整理仍不可靠：原生 `agent_runtime_helpers.py` 在合并连续 user 消息后执行 `drop_stale_api_content`。下一次 API 请求重新带上原包装；合并结果还会回到内存会话历史。
3. 只标为“历史”仍不足以表达真实的取消状态。第五轮虽然实际请求仅剩一份运行包装，问“你好”仍收到旅行散文。该轮协议状态为 completed，但意图验收失败。最终补充真实中断状态，并在请求的 system 视图明确当前回合边界；最后复测恢复为正常问候，没有继续写旧文。
4. 原先的首事件计时将正文、公开工具输出之前的真实响应数据忽略。此前超时样本在约4—5秒已有模型响应，30秒被终止并不代表连接30秒无数据。
5. 截图对应原任务实际在提交后约0.404秒发送请求体、5.48秒收到数据、21.22秒收到正文、23.22秒产生工具事件。显示的31秒是累计任务时间，不能解释成31秒都在初始化。该任务共52.53秒，不能与包含更多工具轮次的任务直接计算加速比例。

## 超时规则

- 请求派发后30秒无响应数据且无公开事件：连接响应超时。
- 已有响应数据，但120秒仍无正文或公开执行事件：首次公开输出超时。
- 连续120秒无模型、工具或正文活动：流无进展超时。
- 整体任务达到30分钟：总执行期限。

这些是保护期限，不是响应速度保证。当前计时器由渲染进程拥有，检查间隔5秒；测试观察到超时与收尾延迟，不能声称精确在120秒终止。不能通过继续放大期限解释或修复生成慢。

## 兼容范围和剩余工作

修复位于应用共享 ACP 桥接和接收链，未另建聊天执行器，也未移除工具或降低推理。当前真实模型验证仅覆盖上述官方 GLM 模型。字节级监测挂接原生 OpenAI-compatible 客户端；其他原生协议主要依靠 ACP 的真实非空更新观察活动，不能声称所有协议已有相同的字节级计时覆盖。Hermes 升级后需重新核对 `_build_api_kwargs` 等兼容入口。

仍未解决的是：部分请求在已收到响应后，长时间不产生正文或公开工具事件，以及渲染进程在长流任务中的定时/收尾延迟。下一步应对同一实际请求体做原生链路与供应商直连对照，记录首响应、内容/工具增量、结束原因和总耗时，辨别输入约束、原生重试和供应商生成行为；同时将严格的期限归属迁到不依赖页面调度的后端。不能用“GLM天生就慢”、降推理、删工具或放宽超时替代证据。
