# 会话字体、间距与 Markdown 排版修复

## 已确认原因

图1对应原会话第263条记录的 structuredEvents[0].message（981字符公开阶段性结果），不是普通 answer 正文。该通道的实时与历史节点均用 textContent，导致标题、加粗、引用及表格标记直接显示。正文通道使用 Markdown 解析，因此同一会话出现两种排版。

历史正文节点已使用 Markdown HTML，但仍带 native-black-ball-text 的 white-space: pre-wrap。HTML 元素之间的换行与段落外边距叠加，制造列表和段落间的大块空白。

另外，章节名称被 promoteNovelChapterHeadings 自动提升为标题；加粗语法在中文紧邻引号时受默认分隔符规则影响；流式稳定区按空行切分，可能把同一个松散列表拆成两份。

## 修改

- 持久公开阶段性结果使用现有渐进 Markdown 渲染器，保持 structured 事件身份，不转换成 answer AST；执行日志和瞬时状态仍使用原来的展示方式。
- 正文与阶段性结果统一字体、字号、1.65行距；粗体继承字号、字体和行高，只提高字重。列表条目间距 .3em，段落间距 .65em；去掉历史正文对 HTML 空白的额外保留。
- 保留模型明确写出的 Markdown 标题层级，取消按章节名称猜测标题。标题随正文设置及缩放同比变化。
- 在现有 Markdown tokenizer 中增加范围限定的中日韩文字与标点强调兼容。代码、未闭合标记保持原样；不使用全局替换把正文强行加粗。答案 AST 与页面使用同样的 tokenizer，原始复制源不变。
- 渐进稳定区按 Markdown 块边界切分，避免在列表、引用或表格中间拆分。完成时保持已绘制正文节点，历史回放使用相同样式。

## 验证

- Electron 排版实测18组：实时/历史/阶段结果，420与900宽度，0.85/1/1.5缩放；核对标题数、列表数、表格、代码、中文引号加粗、列表中粗体与普通字的实际字号/字体/行高以及条目间距。
- 原有 Electron 收尾稳定性12组通过，另4种尾部补齐场景通过；正文节点与选区保持，阶段性内容未丢失。
- Markdown、结果AST、阶段性内容保留15项检查通过；语法和差异空白检查通过。
- 扩展 progressive-typing-render 检查有9项原有源码形状断言失败。读取修改前备份运行同套检查仍为相同9项失败、26项通过，无新增失败。hms-outline 另有1项原有提示词字面断言失败，涉及本轮未修改的 main.js；未修改这些无关断言。
