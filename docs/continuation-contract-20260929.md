## 接续机制

1. 原生通道先持久化补充 ID、内容和接收回执，再调用原生重定向。同 ID 同内容不重复投递，不同内容拒绝。
2. 模型请求期间只重定向模型请求；工具执行期间不再把补充塞进工具输出，而由原生下一次安全边界作为 user 消息接入。
3. 接收与封口共用补充锁。封口前的晚到消息进入同一任务的有界接续；封口后的新消息明确拒绝，由现有队列处理。旧 ID 不改投新轮次。
4. accepted 只表示接收并持久化；applied 只表示构建的 user 输入中确实包含补充。不能将两者宣称为“已理解并完成”。
   原生 redirect 与工具启动竞争时，匹配的补充不允许降级混入工具输出，仍留给下一安全边界；其他原生 steer 不受影响。
5. 模型在实际回复中声明 addressed、needs_clarification 或 failed，回执关联输出。普通答复使用既有 baiqiu-outcome 尾部元数据；阶段结果可使用 v2 元数据，不强制把普通回复改成阶段卡。

## 完成判定

- 原生循环结束不等于用户任务交付完成，阶段 status:completed 也不能替代任务完成声明。
- 全部成果已由阶段结果交付时，最后一个 v2 阶段结果可声明 taskCompletion，指定 status:completed 和实际 deliveredSegmentIds。
- 黑球运行时检查输出引用、待完成工具和补充，再输出终态证据。白球校验本轮身份、引用及内容摘要，不复制阶段正文到答案区，不将任意 completed 当成功。
- 普通正文为空但有效阶段交付证据已到达，沿用原阶段结果，不再仅因答案字段空白报失败。
- 需要用户说明时保留 awaiting_input，不自动续队列或伪装完成；真实协议错误不能被等待状态覆盖。

## 顺序与保留

- 补充实际入请求时封住前一段输出，后续事件和答案段携带 replyToUserMessageId。
- 同一任务保留一个运行状态；新回复段使用现有消息组件，放在对应补充用户消息之后。
- 落库保留完整事件及归属；历史投影按相同字段分组，不依赖文案猜测或到达时间，不重写原有回复。
- 只按相同 eventId 去除重复投递；相同文字的不同事件仍保留。取消和失败保留原始输出。
- 完整消息与显示投影分离：缓存、终态核对和用量统计保留完整消息；补充回复的显示片段不能回写权威消息缓存。活动流收尾期间不被终态快照抢先重建。
- 仅有阶段成果时不因普通正文为空移除已交付行；最终补发的正文保留补充归属。旧数据正文与分段无法对应时保留原消息，不静默丢弃正文。
