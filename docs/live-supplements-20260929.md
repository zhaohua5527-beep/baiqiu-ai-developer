## 投递与回执

每条补充以固定 `supplementId` 绑定原始会话和 `turnId`。主进程先持久化用户原文再投递；相同 ID 重试只查询或重用原生收据，同 ID 不同文字为冲突。

- `accepted`：运行时接受了补充，还不能代表模型已经处理。
- `applied`：补充标记出现在构造完成的模型请求中，不等于供应商成功响应，也不保证语义理解正确。
- `pending` / `cancelled`：补充未确认接入或任务停止，原文仍保留。
- `unknown`：回执不明确，使用同一 ID 重试，三次仍不明确则暂停；不得自动转成另一轮重复执行。

收尾与补充相撞时，原生明确拒收才允许回落至下一轮；不明确的旧回合不得改投新回合。迟到的 accepted 回执不能覆盖 applied、pending 或 cancelled。已发送或回执不明的条目不允许原地修改，可另发补充。

原生已接收但最终未进入请求的补充最多接续一次；仍未确认则明确保留为 pending 并报告未完成，不能无限重试或静默丢失。

接口 `stream_activity` 来自真实收到的字节，在尚无正文时最多每五秒展示一次；字节数不是 token 用量或思考步骤。模型无公开输出时仍可能需要等待，这个修改不宣称降低供应商推理延迟。私有推理不转换为阶段性成果。
