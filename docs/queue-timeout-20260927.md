# 排队误报与 Word 后处理超时修复

## 已核实的故障

2026-09-27，合同会话 `local-96b250f1-bfb5-4c45-8008-34ae238384cb`：

- 16:11:15，DOCX 生成成功，47,365 字节。
- 16:13:49，Word 转 PDF 无进度，前台两分钟监测触发取消；工具随后返回退出码 130。
- 16:14:17，“继续”复用了同一个运行时会话，收到排队确认；客户端将排队确认归类为供应商错误。
- 16:17:10，另一轮有明确的用户取消审计。

两个排队确认不能证明供应商 API 出错。Word 转换的原脚本没有阶段日志，不能确定具体卡在 COM 启动、打开文档还是 PDF 导出。

## 修改

- ACP 客户端在异步初始化前占用会话，阻止初始化期间重入。
- 超时或取消的运行时身份不再被恢复；主进程不重新保存取消结果中的旧运行时编号，清除对应绑定。聊天内容和文件不删除。
- 黑球忙碌时等待上一轮退出，发出带轮次身份的等待/就绪诊断，不再把排队确认作为答案提前结束本轮。等待也支持取消。
- 超时、取消和异常返回继续收集已经落盘的文件证据。
- 无进展超时区分仍有工具未返回与等待模型数据。
- 增加 `services/word-pdf-check.ps1`，通过执行上下文向黑球提供有界的 Word 转换方法：默认 45 秒，隔离 PowerShell 工作进程，记录 COM 操作阶段，仅清理通过窗口句柄及进程启动时间确认归属的 Word 进程。不会按进程名批量关闭 Word。
- 转 PDF 成功不等于版面已检查；返回 `layoutVerified: false`，仍需实际查看 PDF。可选排版检查失败不能否认已有 DOCX 产物。

## 验证与范围

- Node：会话初始化并发、取消后的运行时隔离、生成文件保留、等待诊断与答案分流、工具超时分类，以及现有取消持久化/协议恢复/生命周期/事件边界回归。
- Python：等待上一轮结束、等待时取消、原有工具生成桥接测试。
- PowerShell：语法检查；模拟阻塞工作进程验证超时、DOCX 保留、只清理身份匹配进程。
- 未向真实模型发送测试请求，未启动真实 Word 进行 COM 渲染，未重启正在使用的客户端，未发布安装包。

原有临时 `export_pdf.ps1` 没有改写，也没有对既存 Word 进程执行清理。COM 在取得窗口句柄之前就阻塞时，无法安全确认 Word 进程归属；脚本会停止工作进程，不批量终止用户 Word。
