- Windows Application Hang 事件 1002：2026-09-17 13:53:52，PID 31400（0x7aa8），实际路径为 source-current 的 Electron 43.2.0。WER 类型 AppHangB1，HangType 134217728，系统事件字段为 Unknown。9 月 12、14、15 日也存在该 Electron 的 AppHang 报告，不能把这次反馈解释成短暂动画停顿。

- 在重启后的 PID 25044 同时采集主进程和渲染进程 CPU profile。窗口原生激活再使输入框获焦，采样捕获到主进程多次调用 `loadDb → compactPersistedMessageAttachments → compactPersistedMessagePayload`。

## 修复

`main.js` 的历史 payload 清理改为结构共享：只访问原本需要检查的 updates/raw/result/productResult 等字段；没有需要迁移的字段就直接复用原对象，有变化才复制受影响容器。移除以完整 JSON 序列化判断变化的做法。结果提交路径显式复制将要删除旧字段的顶层对象，保持原来的修改隔离。

没有删减历史正文、阶段性结果、工具事件或附件，没有改变请求协议、推理强度、权限和超时。输入框预热能力仍保留。

## 当前生效情况

当前 Electron 不支持 Debugger.setScriptSource；实时替换尝试在预检查时被拒绝，没有修改进程代码。随后在连续检查确认没有任务、逐字输出、组合输入或未发草稿时，正常退出 PID 25044，再从相同源码和启动参数启动 PID 37872。没有强杀任务，没有更改版本号或顾客发布包。

修复后的原生窗口激活和输入焦点采样没有再出现历史全量比较热点。再执行两组共 10 次 CDP 鼠标点击输入框，一组启用与旧进程相同的 accessibility 状态；主进程和渲染进程均正常响应，辅助功能状态在检查后恢复。

前后原生采样时任务负载、窗口大小不同，不能把两份 CPU profile 当成严格整机 A/B 性能百分比。相同历史数据的内存基准才是本轮可比的量化证据。此次确认并修复了点击路径上的主线程阻塞缺陷；由于缺少原挂起现场线程栈，尚不能宣称所有长期未响应均已根治。
